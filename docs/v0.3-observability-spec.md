# v0.3 规格：节点可观测性与版本管理

状态：已定稿（grilling 2026-10-28），待实现。术语以 [GLOSSARY.md](../GLOSSARY.md) 为准，存储取舍见 [ADR-0009](adr/0009-health-report-in-memory.md)。

## 1. 动机

v0.2.2 真机验证（#62）中，两个问题都是靠翻 hzd 日志、比对打洞候选才找到的：一台 macOS Node 一直跑着修复前的 hzd；云主机安全组没放行 hzd 的 UDP 端口，所有 Node 到它都只能走 Relayed Path。Node 一多，这类问题无法靠人发现。v0.3 让 Admin 在 Admin Console 里一眼看到每个 Node 的版本、直连能力与走 Relay 的原因，并给 Prometheus 提供全网层面的指标。

## 2. 范围

| 编号 | 需求 |
|---|---|
| OB-1 | Node 随 `Hello` 上报软件版本、操作系统、架构；coord 落库 |
| OB-2 | Node 随 `ReportEndpoints` 每 30 秒上报 Health Report |
| OB-3 | hzd 本地判定每个 Relayed 对端的原因 |
| OB-4 | coord 内存保存 Health Report，90 秒过期；`last_seen` 批量落库 |
| OB-5 | 版本比较与健康圆点判定 |
| OB-6 | Admin Console 节点列表新增列与节点详情 |
| OB-7 | `hz node list` 增加版本列 |
| OB-8 | `hzd --version` / `-V`；`hz --version` 带 commit |
| OB-9 | 三个新 Prometheus 指标 |

## 3. 协议（`hz.v1`）

全部为新增 optional 字段，旧 Node 与旧 coord 互相兼容（版本协议 N-2 不变，`PROTOCOL_VERSION` 不需要提升）。

`HelloRequest` 新增：

| 字段 | 示例 | 说明 |
|---|---|---|
| `node_version` | `0.3.0 (a1b2c3d)` | 语义化版本 + commit 短哈希，与 `hzd --version` 同一字符串 |
| `os` | `macos` / `linux` | `std::env::consts::OS` |
| `arch` | `aarch64` / `x86_64` | `std::env::consts::ARCH` |

`ReportEndpointsRequest` 新增 `optional HealthReport health = 8`：

| 字段 | 类型 | 含义 |
|---|---|---|
| `udp4_ok` | bool | 最近一轮 IPv4 STUN 是否成功发出并收到响应 |
| `udp6_ok` | bool | 同上，IPv6；无 IPv6 STUN 目标时为 false |
| `has_stun_mapping` | bool | 是否拿到公网映射地址 |
| `nat` | string | 目前固定 `unknown`（只有一个 STUN 目标，无法判断）；留作扩展 |
| `default_route_virtual` | bool | 默认路由是否由虚拟网卡持有（第三方 TUN 类网络工具开启） |
| `suspicious_endpoint` | bool | 上报的 Endpoint 中有落在 `198.18.0.0/15` 或回环地址的 |
| `direct_peers` | uint32 | 当前 Direct Path 对端数 |
| `relayed_peers` | repeated `RelayedPeer` | 当前 Relayed Path 对端：`node_id` + `reason` |

## 4. Relay 原因（OB-3）

hzd 本地判定，按顺序取第一条命中：

| reason | 条件 | 典型场景 |
|---|---|---|
| `local_udp_broken` | 本机 `udp4_ok` 与 `udp6_ok` 均为 false | #63（macOS 双栈 IPv4 发包 EINVAL） |
| `no_candidates` | 对端在 Network Map 中没有任何可用候选 Endpoint | 对端跑旧版 hzd，STUN 失败，只有 LAN 候选且不在同一局域网 |
| `handshake_timeout` | 打洞信令往来（收到 punch ack），但 WireGuard 握手超时 | 云主机安全组未放行 hzd 的 UDP 端口 |
| `punch_pending` | 已尝试打洞，尚无结论 | 启动后最初 30 秒 |

判定函数是纯函数，输入为本机 netcheck 状态与该对端的打洞/握手状态。

## 5. coord 存储（OB-1、OB-4）

- 迁移 `0005`：`nodes` 表加 `node_version TEXT NULL`、`os TEXT NULL`、`arch TEXT NULL`、`last_seen_unix INTEGER NULL`。`Hello` 时写入版本三列；不带这些字段的旧 Node 保持 NULL，界面显示"未知（< 0.3）"。
- Health Report 只在内存中，键为 node_id，附收到时间。coord 重启后显示"等待上报"。
- 超过 90 秒（3 个上报周期）未收到视为过期：健康圆点为灰，不计入指标。
- `last_seen_unix` 内存实时更新；Network Map 流断开时落库一次，另每 5 分钟批量落库。

## 6. 判定（OB-5）

**版本比较**：只比语义化版本，忽略 commit；基准是 coord 自身版本。

| 情况 | 显示 |
|---|---|
| Node 低于 coord | 黄：版本落后 |
| Node 协议版本已到 `MIN_SUPPORTED_PROTOCOL_VERSION`（再落后就会被拒） | 红 |
| Node 高于 coord | 蓝：高于服务端（升级顺序反了，非异常） |
| 版本相同、commit 不同 | 同版本，界面只显示 commit |

**健康圆点**：自上而下取第一条命中。

| 颜色 | 条件 |
|---|---|
| 🔴 红 | `udp4_ok` 与 `udp6_ok` 均 false；或 `suspicious_endpoint`；或协议版本到支持下限 |
| 🟡 黄 | 版本落后；或 `has_stun_mapping` 为 false；或有 `no_candidates` / `handshake_timeout` 的 Relayed 对端；或 `default_route_virtual`（提示性） |
| 🔵 蓝 | 版本高于 coord |
| 🟢 绿 | 以上皆否 |
| ⚪ 灰 | 离线；或从未收到 Health Report（旧 Node）；或 Health Report 已过期 |

只有 `punch_pending` 不标黄。悬停圆点显示命中的条件。

## 7. 展示（OB-6、OB-7、OB-8）

- **Admin Console 节点列表**新增列：版本、平台（`macos/aarch64`）、最后在线、路径（`3 直连 / 1 中转`）、健康圆点。不新开页面。
- **节点详情**（点开一行）：netcheck 摘要六项，Relayed 对端列表（Node Name + 原因的中文说明 + 对应 runbook 链接，如 `handshake_timeout` → runbook §6.2）。
- **Admin REST**：`/admin/api/nodes` 每个 Node 增加 `version`、`os`、`arch`、`last_seen_unix`、`health`（`color`、`reasons[]`、`report_age_secs`、`direct_peers`、`relayed_peers[]`、netcheck 六项）。
- **`hz node list`**（Admin 专用）增加版本列。普通 User 继续用 `hz status` / `hz netcheck`。
- **`hzd --version` / `-V`**：输出 `hzd 0.3.0 (a1b2c3d)` 并退出，不启动守护进程。`hz --version` 同格式。commit 由 build.rs 从 git 读取，取不到时省略括号部分。

## 8. 指标（OB-9）

标签不含 node_id，序列数不随 Node 数增长。只统计在线且 Health Report 未过期的 Node。

| 指标 | 类型 | 标签 |
|---|---|---|
| `hz_coord_nodes` | gauge | `version`、`os` |
| `hz_coord_relayed_paths` | gauge | `reason` |
| `hz_coord_nodes_unhealthy` | gauge | `check`：`udp4`、`stun_mapping`、`suspicious_endpoint` |

已有的 `hz_coord_punch_*` 与 `hz_relay_node_bytes_total` 不变。

## 9. 不做

- 告警推送（邮件、IM、Webhook）：用 Prometheus + Alertmanager。
- 每个 Node 的中转流量进 Admin Console：继续看 `hz_relay_node_bytes_total`。
- NAT 类型判断：需要第二个 STUN 目标，`nat` 字段先固定 `unknown`。
- Health Report 历史：趋势由 Prometheus 承担。
- 完整的 N² 路径矩阵：只报 Relayed 对端。
